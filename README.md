# TestPing

Плагин для **Spigot 1.12.2** (Java 8): команда `/testping <host>` проверяет
доступность сетевого ресурса в стиле Windows ping — **с самого
Minecraft-сервера**, а не с компьютера игрока:

```
Minecraft Server → Target Host → Minecraft Server
```

## Требования

* Spigot (или совместимый форк) 1.12.2
* Java 8 на сервере (API новее Java 8 не используется)
* Для сборки: JDK 8+ и Maven 3

## Сборка

```bash
mvn clean package
```

Готовый файл: `target/TestPing-1.0.0.jar`.

## Установка

1. Скопируйте `TestPing-1.0.0.jar` в папку `plugins/` сервера.
2. Перезапустите сервер (или `/reload`, но перезапуск надёжнее).
3. При первом запуске создастся `plugins/TestPing/config.yml`.

Команда: `/testping <host>` — работает у игроков (право `testping.use`,
по умолчанию только операторы) и из консоли сервера.

## Конфигурация (config.yml)

```yaml
ping:
  count: 4        # количество запросов (как в Windows ping)
  timeout: 3000   # таймаут одного запроса, мс
  interval: 1000  # пауза между запросами, мс
cooldown:
  seconds: 5      # кулдаун на игрока; на консоль не действует
```

## Как реализован ping

1. `/testping google.com` → проверка права, аргументов и кулдауна (main thread).
2. Запускается асинхронная задача (`Bukkit.getScheduler().runTaskAsynchronously`).
3. DNS-резолв: `InetAddress.getByName(host)` — один раз, IP показывается игроку.
4. 4 раза: `address.isReachable(timeout)` с замером RTT через `System.nanoTime()`
   → «Ответ от IP: время=Nмс» либо «превышен интервал ожидания».
5. Между запросами пауза (`ping.interval`), чтобы не флудить хост.
6. Считается статистика: отправлено / получено / потеряно / % потерь /
   min / max / avg. Если ответов 0 — min/max/avg не вычисляются.
7. Каждое сообщение доставляется обратно в main thread через
   `Bukkit.getScheduler().runTask(...)` — сетевой код никогда не блокирует
   сервер, а Bukkit API не трогается из асинхронного потока.

## Ограничения `InetAddress.isReachable()` (важно)

`isReachable()` — это проверка доступности, а **не гарантированный ICMP ping**.
Его фактическое поведение зависит от ОС и прав процесса JVM:

* **Windows.** JVM обычно использует нативный `IcmpSendEcho`, поэтому ICMP
  работает без прав администратора. Это ближайший к `ping.exe` вариант.
* **Linux.** Чтобы отправлять настоящий ICMP Echo, процессу нужны привилегии
  (root или capability `CAP_NET_RAW`). Без них JVM переходит на запасной
  механизм — TCP-подключение к порту 7 (echo). Большинство хостов и файрволов
  порт 7 закрывают, поэтому **на типичном Linux-сервере возможны ложные
  «100% потерь»** для живых хостов.
  Варианты решения: запускать сервер с правами, выдать Java capability
  (`setcap cap_net_raw+ep /usr/bin/java`) или разрешить ICMP правилами
  файрвола.
* ICMP может блокироваться файрволами/антивирусами и деприоритизироваться
  маршрутизаторами, а замер RTT включает накладные расходы JVM — поэтому
  цифры «приблизительные».
* ICMP-сокеты могут быть дополнительно ограничены контейнерами/Docker.

Именно поэтому в коде и здесь нигде не утверждается, что это «настоящий ICMP»:
это встроенный механизм Java 8 для проверки достижимости хоста.

## Безопасность

* **Никакого `Runtime.exec()`** — пользовательский `<host>` никогда не
  попадает в shell-команду (исключена командная инъекция). Дополнительно host
  проверяется whitelist-паттерном `^[A-Za-z0-9._:-]{1,253}$` (символы имён
  хостов, IPv4 и IPv6).
* Все запросы ограничены: не более `ping.count` (1–10) за раз, таймаут одного
  запроса (`ping.timeout`), пауза между запросами, кулдаун на игрока и запрет
  параллельных проверок — бесконечные потоки и ping-флуд невозможны.
* Вся сеть — асинхронно; main thread не блокируется.
* Все исключения (UnknownHostException, IOException и т.д.) обрабатываются и
  показываются игроку, а не роняют задачу.
* Команда работает и для консоли (без кулдауна), методы только для `Player`
  не используются.
